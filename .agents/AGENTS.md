# Lua Coding Rules

При работе с Lua-кодом пользователя строго соблюдай следующие правила:

## 1. Режимы работы и выбор контекста (ГЛАВНОЕ ПРАВИЛО)
Автоматически переключайся между режимами в зависимости от запроса. Если контекст не понятен — всегда используй **РЕЖИМ 1**.

*   **РЕЖИМ 1: "Разбор и Согласование" (По умолчанию)**
    *   *Триггеры:* Пользователь просто прислал код, спросил "как надо?", "расскажи", "что исправить?" или просит проанализировать.
    *   *Поведение:* **ЗАПРЕЩЕНО** выводить готовый переписанный код целиком. Сначала кратко опиши, что требуется изменить и почему. Затем покажи только изменяемые фрагменты в формате "Было:" и "Стало:". В конце спроси разрешение на изменение и жди команды ("делай"). Перед окончательным форматированием спроси разрешение на удаление закомментированного мусора и выравнивание отступов.
*   **РЕЖИМ 2: "Прямое действие"**
    *   *Триггеры:* Код чужой/нейросети, или если явно указаны команды: "делай", "перепиши сразу", "исправь без согласования".
    *   *Поведение:* Пропусти этап обсуждения и согласования. Сразу выведи готовый, исправленный по всем правилам код без лишних вопросов.

## 2. Ограничение изменений
Фокусируйся только на исправлении явных синтаксических или логических ошибок. Логику и структуру кода оставляй без изменений.

## 3. Область видимости (local)
Проверяй видимость переменных, но учитывай, что программа может быть разбита на отдельные файлы, использующие общие глобальные переменные. Оставляй область видимости переменных такой, какая она есть в исходном коде, если пользователь сам не попросил её изменить.

## 4. Запрет на новые переменные
Используй только те переменные, которые уже есть в коде. **ЗАПРЕЩЕНО** переназначать или переименовывать переменные ради "красоты" кода. Не создавай новые промежуточные переменные для хранения уже существующих значений (не делай "Вася = Васек", а потом "Васек = Василий").

## 5. Заполнение таблиц
**ЗАПРЕЩЕНО** объединять таблицы в литералы через фигурные скобки `{}`. Заполняй таблицы строго построчно через точку (например, `tx.ACCOUNT = firm_id`), так как пользователю легче читать код в таком формате.

## 6. Оптимизация через элементы таблиц
Если позволяет область видимости, используй элементы таблицы напрямую вместо создания отдельных переменных, чтобы уменьшить их общее количество в коде.

*Пример:*
*   *Было (лишняя переменная stop_price):*
    ```lua
    sl.STOPPRICE = tostring(price)
    stop_price = tonumber(sl.STOPPRICE)
    if stop_price > 0 then ... end
    ```
*   *Стало (использование элемента таблицы напрямую):*
    ```lua
    sl.STOPPRICE = tostring(price)
    if tonumber(sl.STOPPRICE) > 0 then ... end
    ```

## 7. Чтение файлов (Кодировка Windows-1251)
Все файлы Lua в проекте сохранены в кодировке Windows-1251. При чтении файлов через терминал принудительно декодируй их в UTF-8, используя следующую команду PowerShell:
`[Console]::OutputEncoding = [System.Text.Encoding]::UTF8; [System.IO.File]::ReadAllLines("ПУТЬ_К_ФАЙЛУ", [System.Text.Encoding]::GetEncoding(1251))`

## 8. Именование переменных и функций

> **Общее правило по опечаткам**: В новом коде опечатки не допускаются. При обнаружении опечаток в существующем коде предварительно сообщи об этом пользователю, но не изменяй их самостоятельно без согласования.

*   **8.1. Приоритет списка именований**: В первую очередь используй переменные из списка именований. Не создавай новые названия, если существующие из списка подходят по смыслу.
*   **8.2. Ограничение новых названий**: Создавай новые переменные с новыми названиями только в случае явной необходимости (если существующие переменные не покрывают нужную сущность).
*   **8.3. Обязательное уведомление**: При создании новой переменной или функции с новым названием в начале своего сообщения обязательно пиши:
    > «Создана(ы) новая(новые) переменная(ые) / функция(и) **<название>** – описание (что делает, зачем нужна, почему названа именно так)».
    Описание отделяй от названия тире или двоеточием согласно правилам русского языка.
*   **8.4. Переменные времени**: Переменные, относящиеся ко времени, временным периодам, интервалам и т.п., именуй в стиле `snake_case` из двух слов, при этом желательно, чтобы второе слово определяло сущность или единицу измерения времени (`time`, `length`, `period`, а также `sec`, `min`, `hour`, `day` и т.д., например: `period_time`, `interval_length`, `bar_period`, `delay_sec`).
*   **8.5. Переменные QUIK**: Переменные, содержащие названия ценных бумаг и связанные с ними значения, получаемые от терминала QUIK, оставляй без изменений или используй строго те имена, которые указаны в документации QUIK (например, `class_code`, `sec_code`, `firm_id`).
*   **8.6. Пользовательские переменные**: Пользовательские переменные, определяемые в коде робота, именуй в стиле `camelCase` (например, `startPrice`, `initPrice`). Исключение составляют переменные из списка именований (например, `max_price`, `min_price`) – их следует использовать в том виде, в котором они даны в списке.
*   **8.7. Локальные функции**: Названия пользовательских функций (не вынесенных в отдельный файл) пиши в стиле `PascalCase` (например, `function Clockwise()`, `function CountDecimals(n)`).
*   **8.8. Функции во внешних файлах**: Названия функций, выносимых в отдельный файл, оформляй в стиле `snake_case` из двух или трёх слов.
    *   *8.8.1.* Если функция используется в коде в единственном варианте (уникальна для данного робота), имя должно состоять ровно из двух слов.
    *   *8.8.2.* Если есть несколько вариантов одной функции или она адаптируется под разные условия, имя должно состоять из трёх слов, где первое слово — название робота (например, `clockwise`), а последнее слово — площадка, терминал, вид ценных бумаг или иной уточняющий признак (например, `spbfut`, `moex`, `stock`). Пример имени файла: `clockwise_sendtransaction_spbfut.lua`.
